> **文档保存事实，聊天处理决策。文档是长期记忆，对话是短期工作台。**

1. 一次对话只处理一个明确的小阶段，例如“阶段 0 回归”或“S2 的 1A 回归样本建立”，避免同时重做 UI、模型、素材和发布。

## 1. 一句话介绍

AdMind 是一个面向长视频平台的 AI 广告决策系统。

它不是简单地“少放广告”，而是依次回答三个问题：

1. **什么时候适合投放？**
2. **暂停后要不要投、用什么形式、放在哪里？**
3. **这个场景在伦理上能不能投？**

对应三个核心场景：

| 场景 | 核心问题 | 主要技术点 | 当前状态 |
| --- | --- | --- | --- |
| S1 高潮避让 | 什么时候投 | 视频语义理解 + 时间段识别 + 规则决策 | 已接入真实 TwelveLabs 分析 |
| S2 暂停保护 | 怎么投、放哪里 | 播放器状态机 + MediaPipe 当前帧检测 + 安全区域评分 | 已完成首版真实链路，仍需扩大素材测试 |
| S3 伦理保护 | 能不能投 | 敏感语义识别 + 伦理硬规则 + 安全兜底 | 已有真实救援素材与 TwelveLabs 结果，展示继续完善 |

## 2. 整体技术架构

```text
视频素材
   ↓
视频 AI 分析（当前使用 TwelveLabs）
   ↓
标准化证据：时间段、场景含义、置信度、风险标签
   ↓
AdMind 决策引擎：伦理规则、播放器状态、广告合同和用户体验
   ↓
生成可执行广告计划 JSON
   ↓
播放器按照计划执行：延后、缩小、移动位置或完全不投
```

最重要的设计思想：

> **AI 负责提供“它看到了什么”的证据，AdMind 负责做最终决定。**

不能让大模型直接决定一切。AI 的输出可能不稳定，而规则必须可测试、可解释、可审计。

## 3. S1：高潮避让

### 要解决的问题

传统播放器可能在固定时间强制插入广告，哪怕此时正好是追逐、打斗、告白、反转或情绪高潮。

AdMind 不只看时间点，而是先理解这一段视频正在发生什么，再寻找自然停顿或情绪恢复段。

### 技术流程

```text
上传视频
   ↓
TwelveLabs 返回带时间戳的场景语义
   ↓
提取高潮、冲突、对白、结尾、恢复段等证据
   ↓
拒绝高打断风险候选点
   ↓
寻找后续安全窗口
   ↓
生成广告开始时间、时长和展示形式
```

### 真正的技术亮点

- 使用视频理解 API 分析的是一段连续视频，不是只识别单张图片。
- AI 返回的不只是“视频里有什么”，还包含事件发生的时间范围。
- AdMind 会把不同供应商的结果转成自己的标准数据结构，未来可以替换模型供应商。
- 最终产物不是一个孤立时间点，而是一份完整、可执行的广告计划。
- 同一个视频可以重复播放，但 AI 只需离线分析一次，结果可以缓存和复用。

### 当前真实完成情况

- 已经使用 TwelveLabs 跑过真实素材。
- CHARGE、Coffee Run、Llamigos 都有真实分析结果。
- 已经能够拒绝高潮点，并把广告移动到更自然的恢复段。
- 不是在网页上手工把广告时间写好后冒充 AI 结果。

### 面试时可以怎么讲

> S1 的难点不只是调用视频 API，而是把不稳定的自然语言分析转成稳定的时间证据，再经过确定性的规则，生成播放器真正可以执行的广告计划。

## 4. S2：暂停保护与安全位置选择

S2 实际上包含两层判断，而且顺序不能反：

1. **暂停后是否应该显示广告？**
2. **如果允许显示，广告放在画面的哪一侧？**

### 4.1 播放器状态判断

系统并不能真正读取用户脑内想法，也不应该这样宣传。

它读取的是浏览器和播放器本来就拥有的交互事件：

- `pause`：用户暂停；
- `play`：用户恢复播放；
- `currentTime`：当前时间点；
- `seeking / seeked`：用户是否正在拖动进度条；
- `timeupdate`：播放时间更新；
- `document.visibilityState`：页面是否仍然可见。

这些都是当前播放器自己的状态，不需要摄像头、麦克风，也不读取其他软件或私人信息。

#### 4.1.1 浏览器究竟能看到什么，不能看到什么

网页能监听的是**自己这一页**和**自己这个播放器**的状态：

| 信号 | 浏览器接口 | 能说明什么 | 不能说明什么 |
|---|---|---|---|
| 暂停 | `video.pause` | 视频停止播放 | 不知道用户为什么暂停 |
| 恢复 | `video.play` | 用户继续播放 | 不知道用户是否真的在看屏幕 |
| 拖动开始/结束 | `seeking / seeked` | 用户正在寻找别的时间点 | 不知道用户寻找的具体目的 |
| 当前时间 | `video.currentTime` | 暂停发生在哪一帧 | 不代表用户喜欢或讨厌该内容 |
| 页面隐藏 | `document.visibilityState === "hidden"` | 当前标签页不再可见，或窗口被最小化 | 不知道用户切去了微信、Word 还是别的软件 |
| 页面可见 | `visibilityState === "visible"` | 页面仍处于可见状态 | 不保证用户的眼睛正在看页面 |
| 窗口失焦 | `window.blur` / `document.hasFocus()` | 当前网页不再接收键盘焦点 | 可能只是点了地址栏、开发者工具或另一个窗口，不能直接断言“离开了” |
| 窗口重新聚焦 | `window.focus` | 当前网页重新获得焦点 | 不等于恢复播放 |

因此当前规则故意保守：

- `hidden` 是明确的取消信号：广告立刻消失，本次机会顺延；
- `visible + blur` 只是“暂缓判断”，不能包装成知道用户去了哪里；
- `play` 和 `seeking` 会终止当前暂停任务；
- 只有“持续暂停 + 页面可见 + 有焦点 + 没有拖动”同时成立，才进入视觉分析。

这不是监控操作系统后台，也没有权限查看用户打开的其他软件。它只是网页前端的事件监听。

#### 4.1.2 播放器状态机在代码里怎么运行

当前首版状态包括：

```text
idle 等待暂停
  ↓ pause
observing 确认暂停是否稳定
  ├─ play / seeking / hidden / blur → deferred 顺延
  └─ 连续 1.5 秒稳定 → analyzing 分析当前帧
                                 ├─ 没有安全位置 → deferred 顺延
                                 └─ 有安全位置 → delivered 展示
```

关键实现路径是：

1. React 给 `<video>` 绑定 `onPause`、`onPlay`、`onSeeking`、`onSeeked` 和 `onTimeUpdate`；
2. `document` 监听 `visibilitychange`，`window` 监听 `focus / blur`；
3. 每次暂停创建一个 observation id，相当于这次异步任务的编号；
4. 如果检测期间用户恢复、拖动或离开页面，就让编号失效；即使旧的视觉结果稍后返回，也不能再弹出广告；
5. 稳定暂停时只把当前 `<video>` 帧交给 MediaPipe；
6. 恢复播放时，卡片、检测框和观察计时全部清理。

observation id 解决的是常见异步竞态：模型正在分析第 20 秒的画面时，用户已经拖到了第 50 秒；没有这层校验，旧结果可能错误地覆盖新画面。

### 状态机示例

```text
用户暂停
   ↓
进入 1.5 秒观察窗口（当前演示阈值，后续需实验校准）
   ├─ 立即恢复播放 → 不投广告
   ├─ 拖动进度条 → 不投广告
   ├─ 页面切到后台 → 不投广告
   └─ 持续暂停、页面可见、没有拖动 → 允许低遮挡广告
```

这项技术更准确的名称是：

> **基于可观察交互信号的观看任务估计。**

它属于事件驱动编程和有限状态机，不是读心，也不是隐私监控。

### 4.2 自动选择左上角或右上角

当状态机判断“可以显示广告”以后，系统才分析广告应该放在哪里。

```text
取得当前视频帧
   ↓
检测人脸、人物、主要物体和高视觉密度区域
   ↓
分别计算左上角、右上角的遮挡风险
   ↓
选择风险更低的一侧
   ↓
如果两侧都不安全，则不显示或继续延后
```

一个简化的安全区域评分可以是：

```text
区域风险 = 人脸重叠 × 5
         + 主体重叠 × 3
         + 文字重叠 × 2
         + 画面复杂度 × 1
```

权重需要通过素材测试继续校准，但整个决策过程是可解释的。

### 可使用的视觉技术

#### 推荐路线：MediaPipe / OpenCV 本地分析

- MediaPipe 可以检测人脸、人物或物体，并返回 bounding box（矩形坐标）。
- OpenCV 可以计算边缘、运动和画面复杂度，作为动画素材识别失败时的兜底。
- 不需要训练大型模型。
- 可以在本地离线处理，API 成本为 0。
- 适合现在的个人项目和 GitHub 开源展示。

#### 可选路线：Google Video Intelligence

- 可以返回人物、物体、人脸在不同时间点的坐标。
- 它不会直接告诉我们“广告应该放左上角”。
- Google 提供坐标证据，最终的安全区域评分仍由 AdMind 完成。
- 需要 Google Cloud 认证和计费账户；目前**尚未接入本项目**。

#### TwelveLabs 在 S2 中的定位

- TwelveLabs 更擅长理解“画面发生了什么”和“什么时候发生”。
- MediaPipe、OpenCV 或 Google Video Intelligence 更适合解决“主体具体位于画面哪里”。
- 两类工具不是互相替代，而是分别解决语义和空间位置问题。

### 两种实现方式

#### 方式 A：离线预分析（测试、固定素材和兜底）

- 每隔约 0.5 秒分析一帧；
- 保存为 `placement-timeline.json`；
- 用户在任意时间暂停时，读取最近时间点的结果；
- 优点是没有等待时间、成本稳定，也更接近视频网站的工业流程。

#### 方式 B：暂停时实时分析（S2 正式路线）

- 用户暂停后截取当前帧；
- 在浏览器本地运行一次 MediaPipe 视觉检测；
- 优点是真正对应任意暂停时间；
- 缺点是第一次加载模型和检测可能有延迟，需要 Web Worker 和预加载优化。

当前首版的正式演示使用“暂停时实时检测”，自动化测试则直接输入不同的人脸矩形 JSON，验证位置评分是否稳定。模型加载失败时页面会明确标记“模型回退”，使用只保护字幕与控制条的保守布局；它不会伪造一次成功的人脸检测。未来素材量变大后，再增加离线预分析 JSON 作为性能缓存与可用性兜底。

#### 4.2.1 当前项目已经接入的真实 MediaPipe 路线

首版已经使用 `@mediapipe/tasks-vision` 的 Face Detector，而不是手工写死广告位置：

```text
稳定暂停 1.5 秒
   ↓
动态加载 MediaPipe WASM 运行环境
   ↓
从网站 public/models 读取 BlazeFace full-range 模型
   ↓
FaceDetector.detect(video) 分析当前已解码画面
   ↓
返回人脸 bounding box（像素坐标）
   ↓
除以 videoWidth / videoHeight，归一化为 0～1 坐标
   ↓
与四个广告候选区域计算重叠风险
```

这里不需要 API Key，也没有逐次调用费用。模型文件跟网站一起发布；MediaPipe 的浏览器 WASM 运行文件目前从固定版本 CDN 加载。别人打开 GitHub 部署的网站即可使用，不需要在自己电脑配置 Python、Google Cloud 或本地服务器。

为什么选 `IMAGE` 模式而不是持续分析整段视频：S2 只需要在一次稳定暂停后检查一帧。持续逐帧检测会浪费 CPU，也会让页面卡顿。当前 `detect()` 是同步推理，但每次暂停只运行一次；如果以后扩展成连续追踪，应把推理移入 Web Worker，避免占用主线程。

#### 4.2.2 广告位置不是模型直接给的，而是 AdMind 算出来的

MediaPipe 只回答“人脸在哪里”，不会回答“广告该放哪里”。AdMind 预先定义四个候选区域：左上、右上、左下、右下，然后执行确定性评分：

```text
人脸框先向外扩张一圈安全边距
   ↓
计算每个候选广告区域与人脸框的重叠比例
   ↓
把底部字幕区和播放器控制条作为保留区加入惩罚
   ↓
风险 = 人脸重叠 × 0.86 + 保留区重叠 × 0.74
   ↓
选择风险最低的位置；最低风险仍超过阈值则不投
```

所有坐标都归一化到 0～1，所以同一套规则不依赖视频是 720p、1080p 还是别的分辨率。当前页面会直接画出人脸框、显示左右风险、最终位置和推理耗时，换一个时间点暂停就会重新计算。

当前诚实边界也要讲清楚：首版真实检测的是**人脸**，并用已知布局规则保护字幕和控制条；它还没有完整识别人物全身、关键物体、屏幕文字和视觉显著性。因此“没有检测到人脸”不等于“画面绝对没有重要主体”。下一阶段可增加人物/物体检测或离线显著性分析。

#### 4.2.3 两部分怎样在网页里合起来

S2 不是一个模型完成的，而是两套能力串联：

```text
第一部分：播放器状态机
回答“这一次暂停能不能投”
        ↓ 只有允许时才继续
第二部分：MediaPipe + 安全区域评分
回答“广告放哪里、是否有安全位置”
        ↓
广告渲染层
按决定显示静音卡片；恢复、拖动、隐藏或失焦时立即撤下
```

“播放器外侧陪伴广告”指网站页面中播放器旁边或下方的广告位，不是用户关闭网页后仍出现在 Windows 桌面。当前首版主要实现播放器内部安全角落卡片；外侧广告位仍是可选产品方案。

### 4.3 暂停广告不能只有一种小卡片

如果所有暂停都只出现同一个静音小卡片，S2 确实容易被理解成“只是把大广告缩小”。更完整的产品逻辑应该同时决定：**要不要投、何时投、放哪里、用多大形式，以及这次没投的商业任务如何补偿。**

建议使用渐进式广告形态，而不是“一暂停就霸屏”或“永远只放小卡片”：

```text
暂停后的短观察期
   ├─ 立即恢复 / 拖动 / 切后台 → 不展示，本次机会转入后续队列
   ├─ 稳定暂停较短 → 安全角落的小型静音卡片
   ├─ 稳定暂停继续延长 → 中型暂停海报或播放器外侧广告
   └─ 长时间无操作且画面安全 → 可升级为大型暂停海报，恢复播放时立即消失
```

“暂停 5 秒后变大”可以作为一个策略，但 5 秒不是已经验证的固定答案，需要通过测试校准。大型广告也不应简单理解为不可关闭的全屏视频；更合理的是使用广告主提前提供并通过审核的多尺寸素材，在不破坏原画面的前提下逐级升级。

短暂停确实可能减少一次广告展示，但这不等于商业失败。AdMind 可以：

- 在桌面端优先使用播放器外侧的即时陪伴广告，不遮挡视频；
- 将未完成的商业任务顺延到下一次稳定暂停或 S1 的安全插播点；
- 只把满足可见性和持续时间要求的展示计为有效机会，避免产生用户根本没看到的低质量曝光；
- 根据活动剩余量和最晚交付时间决定是否升级广告形式，而不是无条件扩大广告。

### 4.4 S2 功能清单：必须让用户知道系统做了什么

| 功能 | 系统做什么 | 商业或体验价值 | 当前状态 | 页面应如何体现 |
|---|---|---|---|---|
| 暂停事件监听 | 读取 `pause / play` | 识别真实暂停机会 | 已有基础实现 | 显示当前播放状态 |
| 稳定暂停计时 | 暂停后持续计时 | 过滤一闪而过的短暂停 | 已实现，首版阈值 1.5 秒 | 实时显示“已稳定暂停 X 秒” |
| 拖动与跳转检测 | 读取 `seeking / seeked` 并统计次数 | 避免在找画面时弹广告 | 已实现会话内统计与取消 | 显示拖动次数与顺延原因 |
| 页面可见性与焦点 | 读取 `visibilityState`、`focus / blur` | 用户离开时不浪费曝光 | 已实现保守判断 | 显示“可见有焦点 / 可见失焦 / 已隐藏” |
| 当前帧人脸检测 | MediaPipe 返回人脸矩形框 | 避免挡脸 | 已真实接入 | 画面绘制检测框，并显示数量与推理耗时 |
| 字幕和控制条保护 | 排除底部字幕、进度条和播放按钮区域 | 保留查看与截图任务 | 已实现确定性保留区 | 风险计算中对底部候选区施加惩罚 |
| 安全位置评分 | 比较四个候选区域的重叠风险 | 不是固定把广告写死在某个角落 | 已实现并有单元测试 | 显示左右风险和最终位置 |
| 渐进式广告形态 | 随稳定暂停时长切换小卡片与扩展卡片 | 兼顾体验与广告交付 | 已实现首版两级形态 | 1.5 秒后小卡片，8 秒后扩展；阈值仍需实验 |
| 长暂停升级 | 长时间无操作且画面安全时允许更大素材 | 提高有效曝光和广告价值 | 已有 8 秒演示规则 | 显示当前形态；不能声称 8 秒是行业最优值 |
| 商业任务顺延 | 本次未投时转到下一安全机会 | 减少保护体验造成的交付损失 | 已实现当前页面会话状态；跨 S1 服务端队列仍待做 | 显示“本次跳过 → 已进入后续队列” |
| 安全兜底 | 模型失败或所有区域危险时不投放/回退 | 防止错误遮挡和演示造假 | 风险拒绝已实现；模型失败目前使用保守布局回退 | 明确显示模型状态和原因 |
| 实时决策证据 | 每次暂停都重新显示状态、检测框和结果 | 证明不是提前写死的演示 | 已接入 S2 页面 | 暂停时实时更新，保持单一区域展示 |

S2 页面最终应直接显示一条随每次暂停变化的实时证据链，例如：

```text
稳定暂停 2.4 秒 → 页面可见 → 最近未拖动 → 检测到 1 张人脸
左上风险 82% / 右上风险 6% → 选择右上角小型静音卡片
```

如果用户换一个时间点暂停，人脸位置、风险分数、广告位置和广告形态都应重新计算。这是证明系统在实时处理，而不是为一个固定时间点预先摆好效果的关键。

### 4.5 跨场景商业任务顺延：让 S1、S2、S3 成为一个系统

S1、S2、S3 不应该只是三个互不相关的 Demo。它们可以共同处理同一条待交付广告：

```text
S2 遇到一次过短或不稳定的暂停
   ↓
本次不强行展示，广告任务进入当前观看会话的待交付队列
   ↓
优先等待下一次稳定暂停，由 S2 再次判断
   ↓
仍未完成时，允许转到 S1 已识别出的自然转场或低打断插播点
   ↓
如果进入 S3 的救援、医疗或灾难伦理保护区间，则继续等待或记录商业缺口，绝不拿 S3 补量
```

这条机制同时解决两个问题：S2 不必为了提高原始触发率而打扰短暂停用户；广告主的任务也不会因为一次保护决定就被直接丢弃。它更准确的产品名称可以是：

> **跨机会广告任务编排（cross-opportunity ad orchestration）。**

正式实现时，待交付队列至少需要保存：活动 ID、可用素材规格、最晚交付时间、已经尝试的机会、失败原因、下一个允许尝试的场景，以及是否命中 S3 硬性保护。Demo 可以先在当前网页会话内保存；真实平台再由服务端进行跨页面和跨设备的商业节奏控制。

### 当前真实完成情况

- 播放器已经具备暂停、恢复、拖动、页面隐藏、窗口失焦和异步任务失效处理。
- 已真实接入浏览器本地 MediaPipe Face Detector，并随每次稳定暂停重新检测当前帧。
- 已实现四候选区域、人脸安全边距、字幕/控制条保留区和风险阈值拒绝。
- 已在页面显示暂停时长、播放器动作、页面状态、人脸数、推理耗时、位置风险与顺延原因。
- 当前只是人脸级首版，尚未实现人物全身、关键物体、OCR 文字和视觉显著性分析。
- 跨 S1 的商业任务队列目前仍是产品流程和页面说明，尚未做服务端持久化。
- Google Video Intelligence 只是备选方案，不能在面试中说成已经接入。

## 5. S3：伦理保护

### 要解决的问题

有些内容即使商业上允许插入广告，伦理上也不应该被娱乐化广告打断，例如：

- 真实救援；
- 医疗急救和严重受伤；
- 儿童危险；
- 灾难和重大公共安全事件；
- 死亡、哀悼和纪念；
- 战争、屠杀等历史或现实创伤；
- 严肃的政府通告、公共安全信息或纪录片片段。

### 技术流程

```text
视频 AI 识别真实救援或高敏感场景
   ↓
AdMind 伦理规则触发硬性保护
   ↓
阻止全屏广告
   ↓
整段不投，或把商业任务重新安排到安全片段
```

### S1 和 S3 的区别

- S1 解决的是“现在打断会不会破坏观看体验”。
- S3 解决的是“在这个语境下投广告本身是否不合适”。
- S1 通常是延后；S3 可以直接否决。

### 商业上如何处理

伦理保护不等于无视广告合同。更合理的方案是：

- 将广告额度重新安排到后面的安全窗口；
- 更换成低打扰形式；
- 更换与语境相容的公益或公共服务内容；
- 记录为什么没有在原计划点执行，供平台和广告主审计。

### 当前真实完成情况

- 海上救援素材已经使用 TwelveLabs 进行真实分析。
- AI 识别到连续救援语境后，AdMind 可以应用确定性的伦理硬规则。
- 最终演示目标：传统方案在固定点插入全屏广告，AdMind 对完整救援段保持无广告。

### 面试时可以怎么讲

> S3 把伦理保护做成优先级最高的硬规则。大模型只提供语义证据，最终否决由确定性规则完成，避免模型输出波动导致在救援或伤亡场景中错误投放广告。

## 6. 决策优先级

商业系统不能只考虑一种目标。AdMind 的建议优先级是：

```text
法律、合规和伦理安全
        ↓
广告合同与频次约束
        ↓
剧情连续性和播放器状态
        ↓
广告收益与投放效果优化
```

这意味着 AdMind 不是“永远让用户舒服”，也不是“永远替平台赚钱”，而是在多个约束下寻找可解释的最优计划。

## 7. 不只是 AI：项目中的工程亮点

### 7.1 供应商适配层

TwelveLabs 的原始输出不会直接散落在网页代码里，而是转换成 AdMind 自己的统一格式。

价值：以后可以替换成其他视频模型，而不必重写整个播放器和决策引擎。

### 7.2 离线处理与结果缓存

视频不是每播放一次就重新调用 AI。

更合理的商业流程是：上传后分析一次，保存结果，之后所有播放请求复用同一份广告计划。这能明显降低 API 成本和延迟。

### 7.3 确定性决策与可审计结果

对同样的证据和规则，系统应得到同样的结果，并能说明：

- AI 看到了什么；
- 哪条规则拒绝了候选点；
- 为什么选择最终时间和形式；
- 如果失败，系统采取了什么兜底方案。

### 7.4 HTTP 视频分段与拖动

线上视频想正常拖动进度条，服务器需要正确支持 HTTP Range 请求和 `206 Partial Content`。

项目已经为媒体文件增加分段响应，使浏览器能够从指定字节位置加载视频，而不是每次都从头播放。这是一个真实的媒体工程问题，不只是前端样式问题。

### 7.5 API Key 安全

- Key 只保存在本地 `.env.local` 或服务端环境变量中；
- 不写入前端源码；
- 不上传 GitHub；
- GitHub 仓库只提供 `.env.example`。

### 7.6 安全兜底

如果模型失败、置信度不足或左右区域都不安全，默认策略应该是“不投或延后”，而不是强行展示。

## 8. 需要真正掌握的关键词

- **Video Understanding**：视频语义理解；
- **Temporal Segment**：带开始和结束时间的视频片段；
- **Computer Vision / CV**：计算机视觉；
- **Bounding Box**：人脸、人物或物体在画面中的矩形坐标；
- **Saliency / Visual Density**：视觉显著性或画面密度；
- **Finite State Machine**：有限状态机；
- **Event-driven Programming**：事件驱动编程；
- **Deterministic Rules**：确定性规则；
- **Offline Preprocessing**：离线预处理；
- **Fail-safe**：发生不确定性时选择更安全的结果；
- **Explainability**：系统能够解释决策原因；
- **Provider Adapter**：把不同 AI 供应商的输出转换成统一协议。

### 8.1 JSON 到底是什么

JSON 的全称是 **JavaScript Object Notation**，文件后缀是 `.json`。它是一种让不同程序交换结构化数据的文本格式，不是专门属于 AI 的“语言”，也不一定由 AI 生成。

AI 服务经常返回 JSON，是因为程序能够稳定地读取其中的字段。例如视觉模型分析一个暂停画面后，可以把结果写成：

```json
{
  "timeSec": 27.4,
  "faces": [
    { "x": 0.08, "y": 0.12, "width": 0.28, "height": 0.42 }
  ],
  "recommendedPlacement": "top_right",
  "confidence": 0.93
}
```

可以把它理解为：模型或程序处理完信息后，按照双方约定好的字段，把“我们想要的数据”装进一个标准数据包，再交给 AdMind 读取。AdMind 项目中的 TwelveLabs 原始输出、归一化视频分析、时间段、候选投放点以及未来的暂停画面位置结果，都可以保存为 JSON，方便代码处理、测试、缓存和审计。

## 9. 面试常见问题与回答

### “这个项目不就是调用了一个 AI API 吗？”

不是。API 只返回视频证据，项目还需要完成：

- 原始结果标准化；
- 候选时间生成；
- 伦理和体验规则过滤；
- 商业约束处理；
- 最终计划生成；
- 播放器执行和失败兜底。

真正的系统价值是把模型能力变成稳定、可执行、可解释的产品能力。

### “AI 判断错了怎么办？”

- 设置置信度阈值；
- 高风险场景采用硬规则；
- 模型不确定时默认不投或延后；
- 保存决策证据，便于复查；
- 后续可以通过更多真实素材校准规则。

### “你怎么知道用户暂停是为了什么？”

系统不知道用户的真实心理，也不声称知道。它只根据暂停时长、恢复播放、拖动和页面可见性，估计当前观看任务是否适合被广告打扰。

### “广告为什么放在左边而不是右边？”

视觉模型先返回人物、人脸和主要物体的位置，AdMind 再分别计算左右候选区域与这些主体的重叠程度，选择遮挡风险更低的一侧。如果两边都不安全，则取消或延后。

### “为什么不直接使用更大的视觉大模型？”

因为这里只需要完成明确、可测量的位置检测任务。轻量模型成本更低、速度更快、隐私风险更小，也更容易在本地部署。大模型不是越大越好，关键是是否匹配任务。

## 10. 约 60 秒项目介绍

> AdMind 是一个面向长视频平台的 AI 广告决策系统。传统广告通常只按照固定时间插入，容易打断剧情高潮、用户暂停操作或严肃救援场景。我的系统首先用 TwelveLabs 对视频进行带时间戳的语义分析，再把模型结果转成统一证据，由确定性的规则引擎综合伦理、播放器状态和商业约束，生成播放器可以执行的广告计划。
>
> 项目包含三个场景：S1 负责避开剧情高潮；S2 根据暂停、拖动、页面可见性和窗口焦点判断是否展示广告，并用浏览器本地 MediaPipe 检测当前帧的人脸、计算遮挡更少的角落；S3 对救援、医疗和灾难等伦理敏感内容执行硬性保护。项目的重点不是单纯调用 API，而是把 AI 输出变成可解释、可审计并能够真正运行的产品决策。

## 11. 这个想法是否已经有人实现，以及为什么仍然值得做

### 先说诚实结论

AdMind 使用的很多单点能力已经存在，不能宣传成“全球第一次使用 AI 优化视频广告”。

行业中已经存在：

- YouTube 使用机器学习寻找长视频中的自然插播点，减少在对白或动作中间插播；
- AWS Rekognition 可以识别黑屏、镜头切换和节目边界，用于自动广告插入；
- YouTube、Prime Video、Disney+、Hulu 等平台已经提供暂停广告；
- Amazon 已公开场景相关的 AI 暂停广告；
- IRIS.TV 在做视频语义、情绪和品牌适配；
- Mirriad 使用 AI 寻找视频内的虚拟品牌植入机会。

因此，以下说法不能使用：

> 第一次用 AI 寻找广告时间。

> 第一次实现暂停广告。

> 第一次根据视频内容决定广告。

### AdMind 的差异在哪里

AdMind 的重点不是发明一个全新的基础模型，而是把原本分散的能力统一成一条可解释的决策链：

```text
什么时候投
   +
暂停后要不要投
   +
如果投，采用什么形式、放在哪里
   +
什么场景必须不投
```

项目目前的差异化方向包括：

- 不只检测静音和转场，还使用视频语义理解剧情高潮、恢复段和敏感语境；
- 不把“暂停”等同于“可以投广告”，而是综合恢复、拖动和页面可见性；
- 如果允许展示，再利用 CV 计算左右安全区域；
- 伦理保护首先考虑观众是否应被广告打扰，而不只考虑广告主的品牌安全；
- 同时纳入伦理、合同、用户体验和商业收益约束；
- 保存 AI 证据、拒绝规则和最终计划，让结果可以解释和审计；
- 供应商可替换，TwelveLabs 只是当前视频理解能力来源。

需要保持谨慎：大型平台有很多未公开的内部技术，因此我们可以说“公开资料中没有发现完全相同的完整链路”，不能声称世界上绝对不存在同类系统。

### S2 需要达到的真正标准

“暂停几秒后再显示广告”本身已经不够成为亮点，因为现有平台也会延迟显示暂停广告。

S2 真正的技术点必须是：

1. 多种播放器事件共同决定是否投放；
2. 视觉模型决定广告的安全位置；
3. 两侧都危险时取消或延后；
4. 整个判断过程可以被用户和面试官看懂。

### 对项目价值的判断

- **作为 GitHub 和简历项目：很有意义。** 它展示真实 API、状态机、CV、规则引擎、媒体工程和产品设计。
- **作为本科项目：完成度和综合性足够高。** 不要求重新发明所有底层算法。
- **作为学术论文：目前原创算法、数据集和实验规模还不够。**
- **作为创业项目：只有原型还不够。** 后续需要平台接入、真实用户数据和商业验证。

已有竞品不是项目失败的证据，而是市场需求存在的证据。项目的价值取决于我们是否真的做出可运行、可解释、可验证的系统，而不是是否第一个想到“广告应该少打扰用户”。

### GitHub 中的推荐定位

> AdMind 是一个面向长视频广告的可解释、多约束决策原型。它结合视频语义理解、播放器交互信号、计算机视觉与伦理规则，统一决定广告何时投、如何投、放在哪里，以及何时必须不投。

### 面试时如何回答“行业不是已经有了吗”

> 行业已经有自动插播、暂停广告和上下文广告等单点能力。我没有声称重新发明这些基础技术；我的工作是把视频理解、播放器状态、空间安全区和伦理规则组合成一条可执行、可审计的决策管线，并用真实 API、真实素材和对比实验验证它。

## 14. 视频优先的四幕滚动叙事（2026-08-16）

展示页当前按“首页 → S1 剧情高点 → S2 用户暂停 → S3 伦理边界”组织为四段连续内容。早期版本曾拦截滚轮并吸附到每一幕，但实际播放器内容高于一屏，用户为了看完视频继续滚动时会被错误送到下一段，因此现在恢复为浏览器原生连续滚动。

- 横向步骤条通过 `IntersectionObserver` 跟随三个真实章节，不替换或隐藏内容；
- 导航不占播放器左侧宽度，三段播放器继续使用单列全宽舞台；
- 章节外框保持低对比，主要层级来自连续背景、环境光、留白和播放器整体阴影；
- 全站不再拦截滚轮，也不使用 CSS 滚动吸附；顶部步骤按钮仍通过 `scrollIntoView` 主动跳转；
- 手机和平板的步骤条允许横向滚动；
- 视频继续使用 `preload="metadata"`，不会在首屏同时解码三个视频；
- 375px 移动端的播放器元信息与操作区改为上下布局，避免标题被按钮挤成竖排。

这套交互属于展示层增强，不改变 S1/S2/S3 的决策逻辑、视频素材或证据来源。

## 15. 播放器控制与“无安全插播点”兜底（2026-08-16）

第 45 版补齐了播放器和 S2 证据展示中的几个真实交互问题：

- 全部视频默认使用 65% 音量，控制条只保留一个标准音量入口，并按高音量、低音量、静音三态切换图标；点击后展开短而细的竖向音量条，拖到最低即静音，点击外部或按 `Esc` 自动关闭；首页自动预览始终静音；
- S2 的拖动计数按一次完整的用户拖动手势统计，不再把同一次拖动中浏览器产生的多个 `seeking` 事件误算成几十或上百次；
- S2 四角位置评分展示“推荐位置”和“风险最高”，即四个候选角落中最低风险与最高风险的对比，不表示把广告从一个对角线位置移动到另一个位置；
- 待交付队列说明位于播放器与证据区下方，以更大字号显示，避免关键信息埋在侧栏底部；
- 首页原有抽象几何动画替换为真实 S1 视频的静音预览，装饰气泡不再承担滚动说明功能。

如果一条视频从头到尾都保持高张力，S1 不应简单得出“永远不投广告”，也不应为了完成商业任务强行插入中贴片。合理的兜底阶梯是：

1. 在整片内部寻找**相对低谷**，即使它不是绝对平静点；
2. 相对低谷低于最大打断阈值时，使用静音卡片、边角小卡或更短素材等低遮挡形式；
3. 如果相对低谷仍超过打断上限，将任务转给片前、片后、稳定暂停、伴随式广告或下一条内容；
4. 记录未完成交付与截止时间，由商业节奏系统后续补偿；
5. 如果进入 S3 救援、医疗或灾难保护语境，继续等待或记录缺口，伦理硬规则永不因补量失效。

当前 Demo 已经实现“允许窗口内不强行插播”和当前页面会话内的顺延表达，但跨页面、跨设备的持久化商业任务队列仍属于后续能力，不能对外宣称已经完成。

S2 的广告生命周期必须区分：

- **尚未展示**：仍在确认稳定暂停或分析画面，此时恢复、拖动、隐藏或失焦会取消本次机会并顺延；
- **已经展示**：小卡片或全屏广告已经出现，此时截图造成的失焦不再回滚任务状态；
- **播放后完成**：用户恢复播放，广告关闭并保留已完成记录；
- **展示后跳过**：用户点击广告关闭或全屏“跳过广告”，保留展示记录，但明确标记为主动关闭；
- **真正顺延**：只有尚未产生展示时失去有效暂停条件，才进入待交付队列。

这一拆分避免把浏览器焦点变化误当成广告投放失败，也避免已经产生展示后重复补量。
